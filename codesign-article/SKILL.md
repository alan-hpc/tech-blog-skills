# 九段式 · codesign 技术报告

**标题就是技术点本身。** 不用悬念式标题，不用「深度解析」这类词。
读者搜的是那个技术点，标题要让搜索命中。

**一句话原则**：
> 资料告诉你怎么用，一手规范与专利告诉你为什么，实测告诉你踩错会怎样。

---

## 1 · 九段骨架

```
# <技术点名称>

<摘要：这篇回答哪几个具体问题。三到五条，每条一行>

## 一、结论与定义        ← 先给答案。读者读完这段就能拿去用
## 二、背景与问题        ← 为什么会有这个东西；不解决会怎样
## 三、核心原理          ← 机制本身，最小可理解模型
## 四、实现细节          ← 约束、参数、边界条件、合法组合
## 五、完整代码展示      ← 可直接编译运行的完整片段
## 六、底层代码展示      ← 上面那段代码生成的 IR / 汇编
## 七、底层原理          ← 硬件为什么这么做（一手规范 / 专利正文）
## 八、实际测试数据      ← 测量口径表 + 数据 + 离散度
## 九、限制与总结        ← 9.1 能支持什么 / 9.2 没验证什么 /
                          9.3 哪些是推断 / 9.4 什么会推翻结论
```

### 每段的硬要求

| 段 | 必须有 | 不能有 |
|---|---|---|
| 一、结论与定义 | 可执行的结论；首现术语的定义 | 铺垫、悬念 |
| 二、背景与问题 | 「不解决会怎样」的具体后果 | 泛泛的重要性论述 |
| 三、核心原理 | 一个最小模型（图或几行伪码） | 一上来就讲全部细节 |
| 四、实现细节 | 约束表、合法组合表 | 只讲能做什么，不讲不能做什么 |
| 五、完整代码 | **能编译、能跑**，含编译命令 | 省略号片段 |
| 六、底层代码 | 五段代码真实生成的 IR/汇编 | 手写的「示意汇编」 |
| 七、底层原理 | 一手依据（规范条款 / 专利段落号） | 「据说」「应该是」 |
| 八、测试数据 | 测量口径表在第一个数字之前 | 无 n、无离散度的数字 |
| 九、限制与总结 | 四个子节缺一不可 | 「未来工作」式的套话 |

### §5 → §6 是这套结构的关键

**第五段的代码，必须就是第六段汇编的来源。**
不能第五段给一个示意版、第六段贴另一个版本的汇编。
读者要能自己编译第五段、得到第六段。**这条不成立，整篇的可信度就塌了。**

### §9 不许省

大多数技术文章不写边界。写了边界，读者才知道哪些能直接用、哪些是你的推测。
**§9.4「什么会推翻结论」尤其重要** —— 没有证伪条件的断言不是结论，是信念。

## 2 · 图：一律 draw.io，禁止 ASCII 画图

**结构图（框 + 箭头 + 分组）一律用 draw.io 画，产出 `.drawio` 源文件与 `.png`，
两个都放进 `diagrams/`。** 源文件让图能被再编辑，PNG 供文章嵌入。

```
diagrams/
  06-d3-FIG2B-CTApair硬件结构.drawio    ← 可编辑源（提交进仓库）
  06-d3-FIG2B-CTApair硬件结构.png       ← 文章嵌入这个
```

### 为什么禁止 ASCII 画图

markdown 代码块用等宽字体渲染**在终端里成立，在 Obsidian / 网页里不成立**：
中日韩字符宽度、字体回退、软换行都会破坏对齐。一张 100 列宽的 ASCII 框图，
在读者屏幕上会被折行成一堆断裂的横线 —— 而作者在编辑器里看是好的，**不会发现**。

| 内容 | 用什么 |
|---|---|
| 框 + 箭头 + 分组的结构图 | **draw.io**（`.drawio` + `.png`） |
| 层次树、简单缩进列表 | 代码块可以，但**每行 ≤ 78 显示列**（中日韩字符按 2 列算） |
| 真实的反汇编 / 日志 / 命令输出 | 代码块，**原样粘贴，不加注释**（见 §3） |
| 时序、流水线重叠 | **draw.io** |

### 生成方式

`shared/mkdrawio.py` 从一份 node/edge 规格同时产出 `.drawio` 与 `.png`：

```python
FIGS = {"06-d3-图名": {"w": 900, "h": 400,
  "nodes": [("tc1", "TC 224", "core", 265, 110, 125, 52), ...],   # (id,标签,类型,x,y,w,h)
  "edges": [("tc1", "tc2", "leader 驱动 follower", "hot"), ...]}} # (源,目标,标签,类型)
```

```bash
python3 shared/mkdrawio.py            # 全部
python3 shared/mkdrawio.py 06-d3-图名  # 单张
```

**配色是语义的，全系列保持一致**，读者靠颜色就能认出类别：

| 类型 | 颜色 | 用于 |
|---|---|---|
| `tmem` | 橙 | 独占存储 / 专用存储 |
| `smem` | 蓝 | 共享存储 |
| `core` | 绿 | 计算单元 |
| `reg` | 灰 | 通用存储 / 寄存器 |
| `dim` | 淡灰虚线 | **不参与**的部分（如被腾空的 CTA） |
| `hot` | 红 | 强调 / 危险 / 关键路径 |
| `grp` | 虚线框 | 分组容器 |

### 两个渲染陷阱（都踩过）

**① 连线标签会盖住连线本身。** 标签的白底矩形若比两个方块之间的空隙还宽，
就会把线整条盖掉，看起来「箭头没画出来」。
**修**：标签偏移到线的上方（横线）或右侧（竖线），不要压在线上。

**② 连线标签会被方块盖住而截断。** 若绘制顺序是「线 → 标签 → 方块」，
超出空隙的标签两端会被后画的方块覆盖，读者看到的是残缺的半句话。
**修**：绘制顺序必须是 **分组框 → 连线 → 方块 → 连线标签**，标签永远最后画。

**每张图生成后必须打开 PNG 看一眼。** 这两个缺陷在规格里完全看不出来。

## 3 · 术语纪律

**首次出现的专业术语必须解释。** 判定方法：

```bash
# 列出全文出现的候选术语与其首现行
grep -noE '\b[A-Z][A-Za-z0-9_.:]{2,}\b' article.md | sort -t: -k2 -u
```

对每个首现位置问：**这一行的上下文，让没见过这个词的人看懂了吗？**

解释可以很短，但要在**首现处**，不能推给后文：

> ❌ `UTCATOMSWS`（详见 §7）
> ✅ `UTCATOMSWS` —— 一条硬件原子指令，在位图上「找一段空闲并占住」

## 4 · 事实 / 推测 / 观点必须分开

三种句子在文章里要有可区分的措辞：

| 类别 | 措辞 | 例 |
|---|---|---|
| **事实** | 「实测」「据 <出处>」「汇编里是」 | 「实测 n=31 中位数 14.0 cycle」 |
| **推测** | 「推断」「按命名习惯推」「疑似」 | 「`SMPOOL` 后缀**推断**指 SM 级资源池」 |
| **观点** | 「我认为」「我的取舍是」 | 「**我认为**这条不值得用，因为调度约束比收益显眼」 |

**混用是最伤可信度的写法。** 一段里把实测、推断、个人偏好用同一种语气写出来，
读者无法分辨哪些能拿去用。

证据等级的完整定义见 [`codesign-sources`](../codesign-sources/SKILL.md) §1。

## 5 · 禁止的写法

| 反模式 | 为什么不行 | 替代 |
|---|---|---|
| 术语堆砌 | 用词密度不等于信息密度 | 每个术语首现给一句解释 |
| 「众所周知」 | 不知道的人就被排除了 | 给出处或简述 |
| 「显著提升性能」 | 没有数字 | 给数字、n、离散度 |
| 「大约是因为」 | 推测伪装成解释 | 标成推断，或去查一手依据 |
| 把 N 次观察写成「定律」 | 无法证伪 | 写成「N 次观察」，并给证伪条件 |
| 「详见后文」解释术语 | 首现处读者已经卡住 | 就地解释 |
| 贴示意汇编 | 与第五段代码对不上 | 贴真实反汇编输出 |

## 6 · 改文章的安全规程

**血的教训**：一次全文正则替换（`re.sub(r" {2,}", " ", s)`）
毁掉了 24 个代码块里 12 个的 ASCII 对齐，无备份，只能手工重建。

1. **改任何文章前，先复制一份到临时目录**
2. **优先用精确字符串替换 + 断言只命中一次**，不要用正则扫全文
   ```python
   assert s.count(old) == 1, "anchor not found or ambiguous"
   s = s.replace(old, new, 1)
   ```
3. 需要批量归一化术语时，用 `shared/norm_safe.py` ——
   它**同时**保护代码块和 wiki 链接
4. 改完立刻跑 `shared/validate.py`

**改章节号时的坑**：「本篇 §8.3」这种**自引用**容易被误判成对别的文章的引用而改错。
自引用要写成无歧义的措辞，不要依赖上下文窗口判断。

## 8 · 常见追问的正确反应

| 用户说 | 真实含义 | 该做什么 |
|---|---|---|
| 「内容太少了」 | 抓来的资料没用够 | 回素材库逐篇过，把没用上的技术点补进对应段 |
| 「专利内容都用上了吗」 | 你只写了附图 | 去读**说明书正文** |
| 「读完了吗」 | 怀疑你只读了权利要求 | 老实说没读完，给页码范围，然后**真的读完** |
| 「不要漏过内容」 | 要穷尽 | 逐段读，每段问「这句话别人说过吗」，没说过就是新内容 |
| 「这个数字靠谱吗」 | 缺 n / 离散度 | 走 `codesign-measure` 的契约补齐 |

**答不上来时直接承认。** 含糊过去的代价，比承认没读完大得多。
