# 素材与证据分级

**立场**：文章里每一条承重断言，都要能回答「你怎么知道的」。
回答不了就不写，或者标成推断。

---

## 1 · 五级证据分级

**每条事实进文章时都带等级。** 混级引用是最常见的失信来源。

| 等级 | 来源 | 措辞 | 能支撑什么 |
|---|---|---|---|
| **E0** | **自己实测**（满足测量契约） | 「实测」 | 行为、数值、踩错的后果 |
| **E1** | **一手规范**：ISA 手册、专利说明书正文、官方硬件文档 | 「据 <文件> §x」/「据 [00xx]」 | 语法、约束、设计意图 |
| **E2** | **厂商工程博客 / 官方演讲** | 「据 <厂商> 博客」 | 用法、推荐做法、标称值 |
| **E3** | **社区博客 / 第三方论文** | 「据 <作者>」 | 用法、他人实测（**非本机数据**） |
| **E4** | **仅检索摘要**（正文没抓到） | 「据检索摘要」 | 仅作线索，**不能作承重依据** |
| **E5** | **推断** | 「推断」/「按命名习惯推」 | 什么都不支撑，只提供假设 |

**红线：**

- **E4 不能写成「据原文」。** 抓不到正文就明说抓不到。
- **E3 的实测数据不能写成「实测」。** 别人在别的机器上测的，要写清是谁、什么机器。
- **E5 必须显式标注。** 助记符拆解、图注推断、「大概是因为」全都属于 E5。
- **标称值 ≠ 测量值。** 厂商标 16 TB/s 是 E2，不是 E0。

## 2 · 抓取渠道

单一渠道找不全，下面这组要都过一遍：

| 渠道 | 抓法 | 默认等级 |
|---|---|---|
| 厂商技术博客 / 大会演讲 | HTTP 抓取 + 正文提取 | E2 |
| 研究机构博客（编译器/kernel 方向） | HTTP 抓取 + 正文提取 | E2–E3 |
| 中文技术社区（知乎等） | 需登录态，见 §2.2 | E3 |
| arXiv / 会议论文 | **下 PDF → `pdftotext -layout`**，不要按 HTML 解析 | E3 |
| 厂商开发者论坛 | 论坛的 JSON API | E3 |
| Reddit / X / 公众号 | 逐个处理；抓不到就标 E4 | E3–E4 |
| ISA 手册 / 官方文档 | 官方站点 | **E1** |
| 专利 | 见 §3 | **E1** |

**存放约定：**

```
sources/<NN-topic>/
  *.pdf                 一手文件
  blogs/*.md            抓到的正文（frontmatter 记 url / 抓取日期 / 等级）
  blogs/figures/        原图
  blogs/FIGURES.json    图注 + 出处 + 原文链接
  SOURCES.md            清单：每条一行，标等级与是否抓到正文
```

### 2.1 抓取质量检查

- **乱码检测**：可打印字符占比 < 0.85 → 删掉重抓
  （典型成因：PDF 被当 HTML 解析）
- **跨话题去重**：同一篇可能属于多个话题，**按内容去重会误删共享文章**。
  按 `(topic, url)` 去重。
- **抓没抓到正文，要在 `SOURCES.md` 里逐条标**。
  这一列直接决定该条是 E2/E3 还是 E4。

### 2.2 需要登录的站点

**不要去读浏览器的 cookie 数据库。**
写一个导出脚本让用户自己导出，cookie 存在**仓库之外**的配置目录
（目录 700、文件 600），**脚本永远不打印 cookie 值**，
并把 cookie 文件名模式加进 `.gitignore`。

## 3 · 专利读法协议

### 3.1 读权利要求 + 附图 ≠ 读完专利

**说明书正文（detailed description）才是主体，通常 50–70 页。**
权利要求是法律措辞，附图是骨架，**正文才有「为什么」**。

一份典型的厂商专利：

| 段落 | 内容 | 处置 |
|---|---|---|
| `[0002]` BACKGROUND | **真正要解决的问题** | ★★★ 必读。**常与所有博客的说法不同** |
| 附图简述段 | 逐图一句话 | 必读，用来划出「发明本体 vs 样板」的边界 |
| 详细描述 | 发明本体 | ★★★ 逐段读 |
| 样板段 | 数据中心 / 通用处理器 / 软件栈框图 | 可跳过，**但要在文章里说明跳过了** |
| 编号条款 | 权利要求 | 读，做成对照表 |

**划边界的方法**：读附图简述，样板图的图注是通用措辞
（「示例数据中心」「处理系统」「软件栈」「访问大模型的系统」）。抽查一张确认。

### 3.2 扫描版 PDF

厂商公开的专利 PDF **常常是扫描图像**：

```bash
pdftotext -layout patent.pdf - | wc -l    # 0 行 → 图像版
```

只能逐页读图。**不要因为 `pdftotext` 无输出就以为读完了。**

### 3.3 自检问题（写文章前必须能回答）

> 「我读了哪些页？正文引用有几处？没读的是什么，为什么可以不读？」

答不上来就是没读完。**把读到的范围写进文章的「一手材料」。**

### 3.4 ★ 引用即须读全：没读正文的专利不能当 E1

**这是一条硬规则：**

> **任何被当作承重依据引用的专利，必须读过它的说明书正文。**
> 只读了权利要求和附图，就只能引用权利要求和附图，**不能标成 E1**。

理由：权利要求是法律措辞，附图是骨架，**设计动机只在正文里**。
一次实际案例：某专利的 `[0002]` 背景段说的动机，与所有博客的说法完全不同 ——
只读权利要求的人永远不会知道这件事。

**语料里的专利分三类，文章必须写清各是哪些：**

| 类别 | 处置 | 在文章里怎么写 |
|---|---|---|
| **已读正文** | 可作 E1，可引 `[00xx]` | 「已读范围：p.54–68（[0002] + [0055]–[0145]）」 |
| **只读了权利要求/附图** | **只能引条款号与图号**，不得引正文、不得标 E1 | 「本篇只用到其权利要求 N 与 FIG. X，未读正文」 |
| **语料里有但没打开** | **不得引用** | 列入「语料中尚未挖掘的部分」 |

**第三类必须显式列出。** 一个话题下有 20 份专利、你只读了 2 份，
读者有权知道另外 18 份没被看过 —— 否则「结合专利」四个字是在暗示一个不存在的覆盖度。

### 3.5 ★ 专利覆盖范围通常宽于实际硬件

这是最容易误导读者的地方。专利会写「3、4、5、10、20+ 个核」，
而工具链只认 2；会写某操作数可以放某存储，而 ISA 手册说不行。

**必须做的**：凡是专利有、手册没有的，**去工具链验证一次**，
把结果写进文章，并明确「**写代码以手册为准，不以专利为准**」。

验证要控制变量 —— 只改一个符号，其余完全相同：

```bash
for V in 1 2 4 8; do
  # 同一份源码，只替换那一个参数
  <编译命令> variant_$V.<ext>
done
# 记录哪些编过、哪些报什么错
```

## 4 · 图表复用

- **能用抓到的原图就不要自己画**，但**每张图必须带出处**。
- 图注要独立成句，说明这张图在证明什么。
- 如果图里的数字与你的正文数字不一致（例如早期版本的笔误），
  **要么改图，要么在图注里显式标出以正文为准** —— 不能放着不管。
